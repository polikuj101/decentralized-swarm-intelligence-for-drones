# Утечка памяти gz-sim (Gazebo Harmonic) в стенде Swarm of Drones — отчёт для разбора

Дата измерений: 2026-10-26. Автор отчёта: Claude Code (Sonnet 5.5) по результатам живых замеров на стенде пользователя.
Цель документа: дать стороннему ревьюеру (другая модель или человек) достаточно данных, чтобы предложить способ починить утечку, не повторяя уже сделанные эксперименты.

## 1. Коротко

- Процесс `gz sim` (сервер Gazebo Harmonic, в `ps` виден как `ruby`, потому что запускается обёрткой `gz`) растёт примерно на **80–240 МБ/мин** (типично ~100–130) пока его сенсоры рендерятся для подписчиков. Без подписчиков и с одним PX4 рост нулевой.
- Ядро Linux (OOM-killer) убивало `gz sim` примерно **раз в 74 минуты**: мир сбрасывается, PX4 теряет оценку состояния, рой оказывается на земле.
- Весь прирост — **анонимная память** (`RssAnon`) в **64-МБ-выровненных областях**, то есть, судя по адресам и размерам, в **пер-потоковых arena-кучах glibc malloc** (`HEAP_MAX_SIZE` = 64 МБ). Файловые маппинги и общая память не растут. Это указывает на утечку (или фрагментацию) в куче, а не на буферы GPU.
- Одновременно процесс уже держит **~3,2 ГБ в swap** при RSS 1,9 ГБ, то есть реальный объём около 5 ГБ, и замеры по одному RSS занижают скорость роста.
- Что точно не помогает: снижение частот сенсоров (рендер упирается в свою скорость, ~10 % выигрыша), программный рендер (не работает с устройствами GPU и в сотни раз замедляет симуляцию без них), проверка здоровья `gz topic -l`.
- Что ещё не проверено и дёшево: `MALLOC_ARENA_MAX`, `jemalloc`/`tcmalloc` через `LD_PRELOAD`, `ogre` вместо `ogre2`, свежая Mesa, обновление драйвера NVIDIA в Windows, профилирование кучи (`heaptrack`).
- Временная мера: сторож `scripts/gz_watchdog.py` корректно перезапускает симулятор, PX4 и агентов при RSS gz-sim ≥ 4500 МБ (если все борты на земле) или ≥ 6500 МБ.

## 3. Что симулируется

5 квадрокоптеров `x500_swarm_1..5` (модель x500_base из PX4 + свои сенсоры), в одном мире `swarm_world`:
- физика ODE, `max_step_size 0.004`, `real_time_update_rate 250`, целевой RTF 1.0;
- плагины мира: Physics, UserCommands, SceneBroadcaster, Contact, Imu, AirPressure, Magnetometer, NavSat и **Sensors с `ogre2`**;
- сцена: пол 100×100 м с процедурной текстурой 2048², 4 коробки-препятствия, 3 цветных диска-цели; тени выключены, сетка выключена.

Сенсоры на каждом борту (из `gen_swarm.py`; все `always_on=1`):

| Сенсор | Тип | Параметры (исходные) | Потребитель |
|---|---|---|---|
| `cam_down` | camera, L8 (моно) | 320×240, hfov 1.2, 15 Гц, гауссов шум 0.007 | VIO (оптический поток) и кадры BDA |
| `lidar_ring` | gpu_lidar | 36 лучей по 360°, 0.2–15 м, 10 Гц, шум 0.02 | обход препятствий |
| `lidar_down` | gpu_lidar | 1 луч, 0.1–30 м, 20 Гц, шум 0.02 | высота (масштаб VIO, управление высотой) |
| imu 250 Гц, navsat 10 Гц, air_pressure | без рендера | — | PX4 |

Итого 15 рендерящихся сенсоров (по 3 на борт). Подписчики: `drone-agent-N` (контейнеры в другой docker-сети, gz-transport через `GZ_RELAY`) — процесс `gz_sensor_bridge.py` подписан на все три топика своего борта и переиздаёт их в ROS 2.

## 4. Симптом и последствия

- Рост RSS процесса `ruby` линейный (см. §5.5). По журналу supervisord `gz-sim` убивался `SIGKILL` в 23:39 → 00:53 (74 мин); `dmesg` показывает три OOM-убийства `ruby` с `anon-rss` 1,8 / 7,5 / 4,35 ГБ (разные размеры из-за swap и давления памяти хоста).
- После каждого убийства мир Gazebo пересоздаётся: модели в точках старта, время симуляции с нуля, EKF PX4 теряет позицию; `flight_ctrl` и HUD продолжают показывать накопленные оценки (раньше без проверок на достоверность), рой оказывается на земле.

## 5. Измерения

Метод: RSS процесса `ruby` из `ps -eo rss,comm` с хоста WSL (контейнерные процессы видны), либо из `/proc/<pid>/status`. Для сравнения «до/после» одного окна использованы 150–200 с. **Разброс одной и той же конфигурации большой: 133–240 МБ/мин.** Единичные замеры нельзя считать различием в 10–30 %.

### 5.1 Изолированный контейнер без подписчиков (3 мин после готовности мира)
Одинаковый образ, отдельный `docker run` (GPU и программный варианты), пропатченный `gen_swarm.py` (варианты в `docs/gz_leak/variants/`).

| Вариант | RSS | Рост |
|---|---|---|
| control (GPU, все сенсоры) | 524 МБ | 0 |
| software GL | 647 МБ | 0 |
| низкие частоты/разрешение | 526 МБ | 0 |
| без камер | 517 МБ | 0 |
| без лидаров | 520 МБ | 0 |
| без сенсоров | 251 МБ | 0 |

Вывод: без подписчиков рост не наблюдается ни в одном варианте. (Возможно, при отсутствии подписчиков рендер вообще не выполняется; это не проверялось отдельно, например по `gz topic -hz`.)

### 5.2 Стенд: что запускает рост
| Состав | Рост |
|---|---|
| свежий `simulator-core` стенда (его сеть и настройки) без клиентов | 0 МБ/мин |
| + 5 PX4 (`fc-*`), агентов нет | 0 |
| + 5 агентов (подписчики сенсоров) | **98 МБ/мин** |
| далее остановить агентов (`docker stop`) | 100 |
| далее остановить и PX4 | **117 МБ/мин (рост продолжается!)** |

Важное наблюдение: **после остановки всех клиентов рост не прекратился** (ещё 3+ мин). Это же видно при остановке только `gz-sensor-bridge`, `vio`, `evidence` внутри агентов. Возможные объяснения (не проверены): подписки остаются «висеть» в gz-transport после `SIGKILL` клиентов (устаревшие записи обнаружения); либо после первого запуска рендера он продолжается независимо от подписчиков; либо утечка не в рендере, а в публикации/обработке сообщений. Стоит проверить `gz topic -i -t /swarm/1/cam_down/image` (список подписчиков) в такой момент.

### 5.3 Подписчики в том же контейнере (`gz topic -e -t ... > /dev/null`, 5 бортов)
| Подписка | Рост |
|---|---|
| все сенсоры (control, GPU) | 133 МБ/мин |
| все сенсоры, программный GL | 0 (но RTF ≈ 0.002–0.02, рендер фактически не идёт, §5.4) |
| низкие частоты/разрешение 160×120 | 65 |
| только камеры | 47–48 |
| только `lidar_ring` (36 лучей) | **166** |
| только `lidar_down` (1 луч) | 67 |
| камеры + `lidar_ring` | 134 |
| повтор control на «новой» Mesa (см. §5.6; обновление не произошло) | **240** |

Значения не складываются (рендер ограничен по производительности), 240 против 133 для одной и той же конфигурации показывает разброс.

### 5.4 Программный рендер (`LIBGL_ALWAYS_SOFTWARE=1`)
- С устройствами `/dev/dxg`, `/dev/dri` внутри контейнера: Ogre не создаёт окно. В логе: `OGRE EXCEPTION(3:RenderingAPIException): OpenGL 3.3 is not supported`, `eglInitialize failed for device EGL_EXT_device_drm`, `libEGL warning: Not allowed to force software rendering when API explicitly selects a hardware device`, `Failed to create dummy render window`; `gz-sim` в цикле перезапускается (сенсоры не рендерятся, поэтому «рост» нулевой — артефакт).
- Без устройств: окно создаётся (ошибок нет), но **RTF ≈ 0.002–0.02** (вместо 1.0), камера выдаёт ~1 Гц при загрузке CPU контейнера ~138 %. Для SITL непригодно. Подозрительно, что CPU использован мало (llvmpipe, возможно, работает в один поток; `LP_NUM_THREADS` не пробовали).

### 5.5 Реальный стенд (5 бортов в полёте, подписчики — агенты)
| Прогон | Заданные частоты | Фактические (D1) | Рост |
|---|---|---|---|
| исходные 15/10/20 Гц | 15 / 10 / 20 | cam 5.7, ring 3.8, down 7.6 Гц | ~90 МБ/мин (549→1490 МБ за 630 с) |
| пониженные 8/5/10 Гц | 8 / 5 / 10 | cam 4.8, ring 2.9, down 5.9 Гц | ~80 МБ/мин (589→1433 МБ за 630 с) |

Фактическая частота — 40–60 % от заданной в обоих случаях: рендер упирается в производительность, поэтому число реально отрисованных кадров почти не зависит от настройки. Рост линейный (≈ +65 МБ за каждые 45 с).

### 5.6 Попытка обновить Mesa (PPA kisak-mesa)
В одноразовом контейнере: `add-apt-repository ppa:kisak/kisak-mesa && apt-get dist-upgrade`. Версия `libegl-mesa0` **не изменилась** (23.2.1), то есть обновление не произошло; эксперимент недействителен и по-настоящему не проведён.

### 5.7 Разбор памяти процесса (`/proc/<pid>/smaps`, интервал 90 с)
```
t0     : VmRSS 1897356 kB  RssAnon 1889340 kB  RssFile 8016 kB  RssShmem 0  VmSwap 3187508 kB  Threads 43
t+90 с : VmRSS 2032248 kB  RssAnon 2024232 kB  RssFile 8016 kB  RssShmem 0  VmSwap 3187492 kB  Threads 43
прирост по маппингам: 134 768 кБ, всё в [anon]; файловые/shmem/stack/vdso/libs: 0
растут (адрес, права, прирост): 7f7124000000 rw-p +65 472 кБ; 7f7130000000 rw-p +35 496 кБ; 7f7128000000 rw-p +33 756 кБ
```
Адреса оканчиваются на `...000000` и области по 64 МБ — характерно для **arena-куч glibc malloc неосновных потоков** (`HEAP_MAX_SIZE`=64 МБ). Значит, растут кучи рабочих потоков (рендер, gz-transport или Ogre). **VmSwap ≈ 3,2 ГБ** — процесс уже вытеснен в swap, реальная скорость роста по RSS занижена.

### 5.8 Что не влияет
- Healthcheck `gz topic -l` каждые 5 с и каждые 60 с: 0 МБ/мин.
- Python-процессы агентов и контейнер `simulator-core` без сенсорных подписчиков: рост нулевой.

## 6. Сопутствующие факты о производительности
- При GPU-рендере RTF ≈ 1.0 (по `/stats`), `gz sim` потребляет ≈ 130 % одного ядра контейнера.
- На стенде `gz topic -hz` измерить не удалось (неверные флаги); частоты считались по числу сообщений в ROS 2 на стороне агента.
- Опыт «снижение частот» не уменьшил число отрисованных кадров, потому что рендер сам упирается в потолок (~6 Гц камера при пяти подписчиках).

## 7. Гипотезы (по убыванию правдоподобия) и что проверить

1. **Утечка/фрагментация в куче рабочего потока (glibc arenas)** — в `gz-rendering`/`ogre-next 2.3.1`/Mesa D3D12 пути или в `gz-sensors`/`gz-transport` при передаче изображений и сканов подписчикам из других контейнеров. Проверки:
   - `MALLOC_ARENA_MAX=1` или `2`, `MALLOC_TRIM_THRESHOLD_=131072`, `MALLOC_TOP_PAD_` — если рост падает, это фрагментация arena, а не утечка.
   - `LD_PRELOAD=libjemalloc.so.2` или `libtcmalloc.so.4` — быстро показывает, виноват ли аллокатор.
   - `heaptrack`/`valgrind --tool=massif` (медленно), либо `ltrace`/`bpftrace` на `malloc` по потокам, чтобы увидеть поток-источник (`/proc/<pid>/task/*/comm`).
2. **Утечка в Mesa D3D12 (23.2.1)** на пути рендера в текстуры/readback для `gpu_lidar` (самый сильный эффект на лидарах: 166 МБ/мин при 36 лучах за 360° — gpu_lidar рендерит несколько проходов). Проверки: Mesa ≥ 24.x (PPA kisak или Ubuntu 24.04 с Mesa 24.0), `ogre` (ogre1) вместо `ogre2` для `<render_engine>`, обновление драйвера NVIDIA в Windows (566.07 → актуальный), `GALLIUM_DRIVER=zink` (на Vulkan) — не проверялось.
3. **Устаревшие подписки в gz-transport** после гибели клиентов (§5.2): сервер продолжает публиковать на мёртвых подписчиков, копя буферы. Проверка: список подписчиков топика и RSS при ожидании > 2 мин после остановки клиентов; запуск клиентов с корректным завершением (`SIGTERM`).
4. **Сенсоры рендерятся всегда, но утечка проявляется только при передаче**. Проверка: `gz topic -hz` без подписчиков, `perf`/`strace -f -e trace=sendmsg` по числу сообщений.
5. **Конфигурация сенсоров** (шум на камере и лидарах добавляет шейдерные проходы; L8-формат; 36 лучей 360° у gpu_lidar). Проверка: варианты без `<noise>`, 90°/180° сектор, RGB8 вместо L8 — в изолированном контейнере с подписчиками (скрипты в `docs/gz_leak/`).
6. **Запуск Gazebo под Windows нативно** (родной драйвер NVIDIA без Mesa D3D12), PX4 и агенты остаются в WSL (gz-transport уже настроен через `GZ_IP`/`GZ_RELAY`). Не проверялось; Gazebo Harmonic под Windows поддерживается хуже.

## 8. Ограничения и требования к решению
- Нужны рендеримые сенсоры: камера (оптический поток для VIO, кадры BDA), кольцевой лидар (обход препятствий) и нисходящий дальномер (высота). Удалять их нельзя без замены: нисходящий можно заменить высотой EKF только с потерей точности (на стенде высота EKF завышена на 0,4–2 м).
- RTF должен оставаться около 1.0 (PX4 в lockstep с Gazebo).
- Платформа: ноутбук с WSL2, 16 ГБ ОЗУ, 4 ГБ видеопамяти; полноценная замена хоста невозможна, ОС Windows нужна пользователю.
- Контейнеры уже собраны из `ubuntu:22.04` (чистая сборка `simulator-core`, 2–3 ГБ дисков); допустимо менять базовый образ/Mesa/Gazebo, если версии `gz-transport13`/`gz-msgs10` остаются совместимыми с контейнерами PX4 и агентов (они на Harmonic).
- Диск C: был заполнен до 100 % (теперь ~16 ГБ свободно); сборки образов нужно планировать с учётом места.

## 9. Что уже сделано (временная мера)
`scripts/gz_watchdog.py`: каждые 30 с читает RSS `ruby` в контейнере симулятора. При ≥ 4500 МБ и всех бортах на земле (высота из Gazebo, не из HUD) или ≥ 6500 МБ сразу — корректный перезапуск: остановить агентов и PX4, перезапустить `simulator-core`, дождаться healthy, поднять PX4, затем агентов, дождаться телеметрии 5/5. Проверено вживую: ~75 с, RSS после перезапуска ~530 МБ. Пауза на время тестов: файл `logs/.watchdog_pause`. Журнал: `logs/gz_watchdog.log`. Перезапуск сбрасывает мир и прогресс миссии. **Замечание:** порог по RSS не учитывает swap (VmSwap), поэтому реальный объём процесса больше.

## 10. Воспроизведение
Все скрипты лежат в `docs/gz_leak/` (запускать в WSL из корня проекта; контейнеры стенда будут остановлены/пересозданы):
- `gzexp.sh`, `gzexp5.sh`, `gzexp6.sh` — изолированные контейнеры с вариантами сенсоров и подписчиками (`gz topic -e`), замер роста RSS за 150 с;
- `gzexp4.sh` — стенд: свежий simulator-core → + PX4 → + агенты;
- `gzexp3.sh` — проверка гипотезы про healthcheck;
- `sw_valid.sh` — проверка программного рендера (ошибки Ogre, RTF, частоты);
- `mesa_test.sh` — попытка обновить Mesa (в текущем виде обновление не происходит);
- `smaps.sh` — разбор прироста по маппингам процесса;
- `variants/gen_*.py` — варианты `gen_swarm.py`;
- `live_driver.py`, `live_rates.py`, `collect.py`, `analyze.py`, `zerr.py` — живой замер на стенде с 5 бортами и сверка с позами Gazebo.

Минимальный воспроизводимый случай (из §5.3): контейнер `swarm/simulator-core:latest` с GPU-устройствами, после готовности мира запустить `gz topic -e -t /swarm/N/lidar_ring/scan > /dev/null` для N=1..5 и снять `ps -eo rss,comm | grep ruby` через 45 с и ещё через 150 с.

## 11. Вопросы ревьюеру

2. Известны ли утечки Mesa d3d12 23.2.1 / ogre-next 2.3.1 / gz-rendering 8.2.3 на `gpu_lidar`/`camera`, зафиксированные в трекерах, и есть ли исправления в более свежих версиях, совместимых с Harmonic?

## 12. Итог (2026-10-26): причина найдена и устранена

**Причина — ошибка в Mesa d3d12**, не в Gazebo, Ogre или драйвере NVIDIA. В `src/gallium/drivers/d3d12/d3d12_cmd_signature.cpp:68`:

```c
struct hash_entry *entry = _mesa_hash_table_search(ctx->cmd_signature_cache, &key);   /* надо: key */
```

`key` уже указатель на ключ, а поиск идёт по адресу этого указателя на стеке, поэтому кэш никогда не срабатывает. Каждый косвенный draw-вызов (`d3d12_draw_vbo` → `ExecuteIndirect`, его использует Ogre-next GL3Plus) создаёт новый `ID3D12CommandSignature` и кладёт его в кэш навсегда. Объекты освобождаются только вместе с GL-контекстом. Поэтому утечка пропорциональна числу проходов рендера (~10–12 КБ на проход, §5.5), а не размеру сообщений. Та же строка есть в Mesa 26.2.5, так что обновление Mesa, Ubuntu 24.04, `wsl --update` и новый драйвер NVIDIA её не исправляют.

**Как найдено** (отдельный контейнер `swarm/simulator-core`, 15 подписчиков `gz topic -e`, стенд не трогался):
- `malloc_info` до и после 92 с: растёт одна арена glibc (+204 МБ), свободных кусков 0,2 МБ до и после; `malloc_trim(0)` освобождает ~4 МБ. Это утечка, а не фрагментация (ответ на вопрос 1).
- `heaptrack` (запуск `heaptrack ruby /usr/bin/gz sim ...`: с `heaptrack gz sim` запись пустая, потому что shebang `#!/usr/bin/env ruby` теряет `LD_PRELOAD`; `heaptrack -p` 1.3.0 не подключается на glibc 2.35). Источник: `libd3d12.so` ← `libd3d12core.so` (~245 МБ за 9 мин) и драйвер NVIDIA `libnvwgf2umx.so` (~77 МБ). Вызовы идут из `Ogre::GL3PlusVaoManager::_update()` (сброс кадра, в основном `gpu_lidar`) и `GL3PlusAsyncTextureTicket::downloadFromGpu` (чтение кадра камеры).
- С `libgl1-mesa-dri-dbgsym` все места утечки сходятся в `create_cmd_signature` ← `d3d12_get_cmd_signature` ← `d3d12_draw_vbo` (`d3d12_draw.cpp:1239`).

**Исправление:** пакеты Ubuntu `mesa 23.2.1-1ubuntu3.1~22.04.4`, пересобранные с однострочным патчем как `+swarm1`, лежат в `docker/simulator-core/mesa/` (там же патч и команда пересборки). Dockerfile ставит 5 пакетов, которые уже есть в образе, и держит их `apt-mark hold`.

**Проверка:**

| | Mesa 23.2.1 (стоковая) | Mesa 23.2.1+swarm1 |
|---|---|---|
| Отдельный контейнер, 15 подписчиков | 131–134 МБ/мин | 0 / 2 / 0 МБ/мин (3 окна по 2 мин) |
| Частоты на борту 1 (камера / кольцо / нижний, сообщ. за 20 с) | 149 / 96 / 195 | 162 / 106 / 202 |
| Стенд, 5 агентов, рой в полёте | ~90 МБ/мин, OOM ~раз в 74 мин | 422 → 437 МБ за 16 мин, с 17:15 без изменений; swap 0, OOM 0 |

Данные сенсоров на одной сцене совпадают со стоковой Mesa: кадр камеры (mean 177,9, std 10,5 на всех бортах), у кольцевого лидара то же число конечных лучей и `inf` на тех же лучах. `lidar_down` на земле даёт `inf` в обоих случаях: до пола ближе `range_min` 0,1 м.

**Что из §7 и §11 больше не актуально:** гипотезы 2–6 и меры с аллокатором (`MALLOC_ARENA_MAX`, jemalloc), свежей Mesa, ogre1, zink, нативным Gazebo под Windows. Сторож `scripts/gz_watchdog.py` можно оставить как страховку: при нормальной работе его пороги больше не достигаются.

**Поправка к §3:** физику считает DART (`libgz-physics-dartsim-plugin`), а не ODE; `<physics type="ode">` в SDF задаёт только тип решателя.

**Не сделано:** о баге в Mesa не сообщено. Если образ переедет на другую версию Mesa, патч нужно применить и к ней.
