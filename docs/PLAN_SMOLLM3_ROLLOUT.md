# План внедрения SmolLM3-3B для разбора приказов (после показа)

Статус: **план, не реализован**. Решение владельца 2026-10-27: стенд до показа не трогаем, внедрение после.
Все цифры ниже — замеры 2026-10-27 в WSL (16 ядер, лимит WSL 10 ГБ, стенд работал). Скрипты замеров — в `docs/smollm3_eval/`.

## 1. Зачем

Правила `swarm/order_rules.py` разбирают зоны и явно названные параметры. Всё, что в приказе выражено смыслом, а не ключевыми
словами («объекты на земле не нужны», «нужен лишь факт наличия»), решает модель. Qwen2.5-0.5B здесь около половины верных ответов.

Набор из 24 приказов без слов для правил (12 английских, 12 русских), модель в связке с `order_rules`, без примеров в подсказке:

| Модель (Q4) | Верно целиком | Англ. | Рус. | `on_target` | p50 | Память (RSS) |
|---|---|---|---|---|---|---|
| Qwen2.5-0.5B (сейчас) | 12/24 | 7/12 | 5/12 | 7/14 | 1,3 с | 0,64 ГБ |
| Qwen2.5-1.5B | 14/24 | 7/12 | 7/12 | 8/14 | 2,5 с | 1,86 ГБ |
| Qwen3-1.7B | 13/24 | 6/12 | 7/12 | 7/14 | 2,8 с | 2,05 ГБ |
| **SmolLM3-3B** | **16/24** | **9/12** | 7/12 | **12/14** | 4,7 с | 3,04 ГБ |

Оговорки: набор мал, ожидаемые ответы размечал я сам; разница в 1–2 приказа — шум. Заметный разрыв только по `on_target`
(12/14 против 7–8/14). Четыре приказа («park at the final waypoint», «wait there for further orders» и их русские пары)
не решает ни одна модель: после коммита 9fea8eb модель не может выставить `rtb_on_complete=False`, это сознательно.

Что НЕ улучшится: сценарий «Браво» и 20 приказов `verify_tasking.py` уже проходят на 0.5B (20/20 на живых бортах).
Выигрыш — только свободные формулировки без ключевых слов.

## 2. Ограничения архитектуры

1. **0.5B на борту остаётся.** `llama-server` в каждом агенте (`supervisord.conf`: `-t 2`, `-c 2048`) обслуживает ещё и Систему 2
   (`planner_bridge.py`, фазы ISOLATED / SWARM_LOSS / CRITICAL). Борт в изоляции не дотянется до общего сервиса. SmolLM3 — только для
   разбора приказа до взлёта, пока C2 жив.
2. **Образ `drone-agent` не трогаем** (llama.cpp b4600 остаётся для Системы 2): b4600 не знает архитектуру `qwen3`, а поведение
   Системы 2 на новом llama.cpp не проверено. Новый llama.cpp — только в новом сервисе.
3. **Пять вызовов в один сервер не годятся.** Сейчас HUD (`/api/tasking`) шлёт приказ всем пяти бортам, каждый компилирует сам.
   Замер (одна и та же модель, новый приказ, 5 одновременных запросов):
   | Конфигурация | Время последнего ответа |
   |---|---|
   | 1 слот, `-t 4` | 20,1 с |
   | 1 слот, `-t 2` (как у бортов) | 25,8 с (таймаут HUD 25 с) |
   | 5 слотов, `-t 4` | 36,5 с (процессор делится) |
   Один вызов: 3,7–4,5 с даже при кэше подсказки (кэша ответов нет); первый после старта 10–15 с.
   Вывод: **компилировать один раз и раздавать остальным бортам** через существующий `POST /v1/manifest`
   (путь «выравнивания» в `post_tasking` уже есть, манифест проверяется `manifest_check`).

## 3. Память (главный риск)

- SmolLM3: **3,2–3,4 ГБ RSS** и почти не зависит от `-c`/`-b`/слотов (3,25 / 3,33 / 3,41 ГБ в трёх конфигурациях).
- Сейчас занято 6,0 ГБ из 9,9 ГБ → с сервисом около 9,3 ГБ при лимите 10 ГБ. Раньше именно OOM убивал gz-sim.

Варианты:
- **(a)** `.wslconfig`: `memory=12GB` (хост 16 ГБ, Windows остаётся 4 ГБ): рискованно для хоста.
- **(b, рекомендуется)** держать сервис только на время ввода приказа и останавливать перед взлётом (`docker compose stop llm-tasking`).
  Сценарий `run_demo.sh` делает приказ до взлёта; для ручного ввода в HUD нужен хук «после вердикта приказа».
- **(c)** меньший квант (около 1,7 ГБ файл вместо 1,9): выигрыш небольшой, проверять качество заново.

Решение принять до реализации; без него сервис в стенд не включать.

## 4. Что сделать

1. **Сервис `llm-tasking`** (compose-профиль, не в основном запуске):
   - образ из llama.cpp **b11483** (`docs/smollm3_eval/llama_new.Dockerfile` — рабочая заготовка); сборка 6 мин;
   - архив проверять по sha256 до распаковки. Снят **один раз**: `4061b98ca882b084c0c580c59c6fb170f296d181ac29cba21ab7d2d90e1c1ec5`
     (по правилу проекта снять ещё раз независимо до включения в Dockerfile);
   - модель `SmolLM3-Q4_K_M.gguf` из `ggml-org/SmolLM3-3B-GGUF`, sha256 `8334b850b7bd46238c16b0c550df2138f0889bf433809008cc17a8b05761863e`
     (совпал с LFS-указателем 2026-10-27), проверка в Dockerfile;
   - запуск `-c 1024 -b 256 -ub 256 -np 1 -t 4`, только сеть mgmt, порт на хост не публиковать, `mem_limit: 3600m`;
   - прогрев: один холодный запрос при старте (иначе первый приказ ~10–15 с).
2. **`swarm/tasking.py`:** отдельный `TASKING_LLM_URL` (по умолчанию как `LLM_URL`), подсказка в формате ChatML с отключённым
   «размышлением» (`<think>\n\n</think>\n\n` после `assistant`, это сделано в `docs/smollm3_eval/hard_orders_bench.py`).
   Если сервис недоступен — как сейчас: правила + значения по умолчанию (`llm_error`).
3. **`docker/web-hud/main.py` + `order_consensus.py`:** один вызов компиляции на одном борту, остальным четырём `POST /v1/manifest`;
   вердикт APPLIED/REJECTED/UNCONFIRMED по ответам пушей. Тесты HUD (сейчас 51) расширить.
4. **Скрипты:** запуск/остановка сервиса в `swarm_fresh.sh` / `run_demo.sh` (вариант b), порог задержки в `verify_tasking.py`
   (p95 4 с для SmolLM3 недостижим: ожидать ~5 с, холодный старт ~10 с → порог 8–10 с, это решение владельца).
5. **Тесты:** `tests/test_order_rules.py` (адрес/шаблон), `docker/web-hud/tests/`; прогнать наборы агентов (сейчас 244) и HUD.

## 5. Проверка и критерии приёмки

1. `verify_tasking.py` на живых бортах: 20/20 по точности (не хуже 0.5B), манифесты одинаковы на всех бортах, p95 в новом пороге.
2. Набор 24 приказов (`docs/smollm3_eval/hard_orders_bench.py`) через настоящий конвейер на живом сервисе: не хуже 16/24.
3. **2–3 полных репетиции демо с запущенным сервисом** (память, gz-sim не падает, OOM нет, watchdog не срабатывает).
4. Отказ сервиса: остановить `llm-tasking` посреди приказа — приказ всё равно компилируется правилами, борты летят.

## 6. Время и риски

Инженерная часть 3–4 часа, живая проверка около 1,5 часа (ожидание прогонов).
Риски: память у предела WSL; вторая точка отказа перед приказом (HUD → один борт → остальные); расхождение с повествованием
«каждый борт компилирует сам» (на момент приказа C2 жив, но это надо помнить при рассказе инвесторам); новый llama.cpp
собирается из архива с одним снятым sha.

## 7. Не входит в этот план

Смена модели Системы 2; GPU-запуск; обучение; расширение словаря правил (дешевле и надёжнее модели для закрытых формулировок).
