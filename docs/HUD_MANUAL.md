# HUD (Swarm Mission Control): как читать экран и куда уходит приказ

Адрес: http://127.0.0.1:8000 (открывать в браузере на Windows, стенд должен работать: `./scripts/swarm_fresh.sh`).
Статус в правом верхнем углу: «HUD online» — страница получает данные; «HUD offline» — нет связи со стендом (WSL выключен или контейнер web-hud не запущен).

## 1. Что где находится

| Область | Что показывает |
|---|---|
| **Верхняя полоса** | «EW: GREEN/JAMMED» — состояние РЭБ; «эпоха N · задач готово a/b · живых бортов n» — эпоха консенсуса (растёт при каждом изменении состава или перераспределении задач) |
| **Поле приказа** («Отправить приказ (Pre-Flight)») | Текст приказа оператора, см. раздел 2. Под полем появляется «Скомпилированный Task Manifest» |
| **Карта (слева сверху)** | Квадраты — сектора с именами: **Альфа S0, Чарли S1, Дельта S2, Эхо S3, Браво S4, Фокстрот S5** (подпись «Браво S4» = зона Браво, внутренний номер 4). Серые прямоугольники — препятствия. Цветные кружки без подписи D — цели T0 (светлая), T1 и T2. Кружки D1–D5 — борта, подпись «высота · источник позиции» (PX4 — позиция от автопилота, VIO — по камере, «⚠GPS» — GPS признан подозрительным). Заливка сектора: цвет борта — сектор сейчас обходит этот борт; зелёная — выполнен; пунктирная рамка — сектор разделён на части |
| **Граф связи (справа сверху)** | Пять узлов-бортов, линии между ними — каналы mesh. Зелёная линия — связь есть (цифра q — качество 0…1), красная пунктирная — потеряна. Красное кольцо вокруг борта — «JAMMED / C2 LINK LOST» (связь с оператором потеряна); серый узел — борт не отвечает |
| **Карточка борта** (под графом) | GPS, NAV (состояние, источник, σ), «Фаза/S1» (фаза и задержка System 1), препятствие, текущая задача, mesh |
| **«Бортовой планировщик и события»** (слева снизу) | Журнал: события роя (• epoch, start task, peer … DEAD, phase …) и решения System 1/System 2 с вердиктами APPLIED/FALLBACK/REJECT, см. раздел 4 |
| **BDA Evidence Gallery** | Карточки-доказательства: кадр с обведённым диском, борт, цель, источник позиции, пометки о том, чем вычислено |
| **Управление РЭБ** (справа снизу) | Кнопки воздействия на стенд, см. раздел 5 |

## 2. Куда уходит приказ

1. Вы вводите текст и нажимаете «Отправить приказ (Pre-Flight)». Браузер отправляет `POST /api/tasking` в **web-hud** (`docker/web-hud/main.py`). Доступ только из операторской сети (`guard`), длина 1…500 символов.
2. **web-hud** отправляет этот текст **каждому из пяти бортов**: `POST http://<IP борта>:9091/v1/tasking` с бортовым токеном (`EW_TOKEN`).
3. На **каждом борту** сервис `tasking` (`swarm/tasking.py`) компилирует приказ:
   - `order_rules.py` берёт из текста то, что однозначно: зоны («Браво», «все квадраты»), реакцию на цели (SKIP / DWELL_ONLY / DWELL_RECON), секунды зависания, возврат или удержание. Приказ без зон отклоняется (HTTP 422).
   - Только для полей, которых в тексте нет, спрашивается **локальная модель** Qwen2.5-0.5B (`llama-server` на этом борту, порт 8080, температура 0, ответ ограничен грамматикой `manifest.gbnf`). Зоны из ответа модели не берутся никогда. Ответ модели `rtb_on_complete=False` отбрасывается.
   - Получается Task Manifest: зоны, `active_sectors`, `on_target`, `dwell_s`, `rtb_on_complete`, `parsed_by` (откуда взято каждое поле: «из текста», «модель», «по умолчанию»).
   - Манифест проверяется (`manifest_check`) и записывается в том борта (`/opt/swarm/state/manifest.json`).
4. **web-hud** собирает ответы пяти бортов и сверяет манифесты (`order_consensus`). Если борты скомпилировали по-разному, остальным раздаётся манифест большинства (`POST /v1/manifest`).
5. **Координатор** на каждом борту (`swarm/coordinator.py`) сам читает файл манифеста: при смене id или подписи перестраивает список задач (только выбранные сектора), и дальше идёт обычный аукцион CBAA/CBBA.
6. HUD считает приказ «принятым», только когда в телеметрии борта те же сектора с источником «operator» (не просто ответ HTTP 200 от компиляции).

Важно: приказ даётся **до** потери связи (пока C2 жив). Если рой ждёт приказа дольше `MANIFEST_WAIT_S` (в `.env` сейчас 900 с), он сам берёт все сектора.

Соответствие зон и секторов: Альфа=S0, Чарли=S1, Дельта=S2, Эхо=S3, **Браво=S4**, Фокстрот=S5 (`ZONE_TO_SECTOR` в `swarm/tasking.py`, задано вручную; Браво намеренно указывает на сектор с целью T0). Цели T1 и T2 лежат в секторах S2 и S3 (Дельта и Эхо).

## 3. Сценарий демо по шагам (что должно быть видно)

1. Приказ «Разведать квадрат Браво…» → под полем манифест с `Браво = S4`, при контакте — доразведка (DWELL_RECON).
2. Борта взлетают на разных высотах (около 3–6 м): это защита от столкновений, а не «каждый сам по себе».
3. Через ~25 с от взлёта включается РЭБ: «EW: JAMMED», красные кольца и «C2 LINK LOST». GPS отключается на 45 с, борта переходят на позицию по камере (VIO), фаза DEGRADED_NAV.
4. Рой продолжает без оператора. Сектор Браво подсвечивается цветом борта-исполнителя, в журнале «start task Браво».
5. Через ~100 с борт 2 «поражён» (его агент останавливается): линии к нему пунктирные, «живых бортов 4», в журнале «peer 2 DEAD», остальные перераспределяют задачи.
6. Исполнитель зависает над целью, во вкладке BDA Evidence Gallery появляется карточка. Потом возврат на базу и посадка.

## 4. Журнал: теги и вердикты

- **S1** — System 1, быстрый тактический контур (`swarm/system1_controller.py`), работает без LLM.
- **S2** — System 2, стратегический советник на LLM (`swarm/planner_bridge.py`), включается только в фазах ISOLATED / SWARM_LOSS / CRITICAL.
- **APPLIED** — команда принята и применена; **REJECT** — отклонена координатором (например, «peer still alive»); **FALLBACK 20.0с** — советник S2 не ответил за 20 с (таймаут), действие не выполнено.
- «• epoch → N (…)» — изменение эпохи консенсуса; «task Браво DONE» — сектор выполнен; «phase → …» — смена фазы борта.

## 5. Панель «Управление РЭБ»

Выбираете борта галочками и нажимаете:
- **Обрыв C2 / Вернуть C2** — потеря и возврат связи с оператором.
- **GPS: применить / Вернуть GPS** — режим denied (GPS отключён), drift или spoof (подмена со скоростью, курсом, целью), длительность в секундах.
- **Mesh L1…L4 / Вернуть mesh** — уровни потерь в сети между бортами; L4 — 100 % потерь.
- **Split {1,2,3}|{4,5}** — жёсткое разделение сети на две группы, автоснятие через 120 с. **Heal** — вернуть связь и запустить таймер слияния (KPI слияния).
- **Сценарий** — запуск заготовленного сценария РЭБ (для демо — `05_investor_demo`: обрыв C2 и GPS denied 45 с).
Изменяющие вызовы идут через web-hud в ew-controller с операторским токеном (`EW_ADMIN_TOKEN`), бортового токена для этого недостаточно.

## 6. Что на самом деле делает System 1 (замер 2026-10-28, один прогон «Браво»)

System 1 — не LLM и не «умный промпт». Это быстрый выбор из короткого списка допустимых действий:
- Раз в такт состояния (около 5 Гц) определяет фазу борта (NOMINAL, DEGRADED_COMMS, DEGRADED_NAV, ISOLATED, SWARM_LOSS, CRITICAL), строит список допустимых для этой фазы действий (`candidates.py`: SCAN_TARGET, HOLD_SECTOR, EVADE_JAMMING, HOLD_POSITION, RETURN_HOME, DECLARE_FAILOVER) и выбирает одно или «ничего» (`matcher.py`: режим hybrid = правила, при промахе сравнение с эталонами через небольшую ONNX-модель эмбеддингов).
- Команда уходит координатору, который проверяет и применяет её (например «prefer T0» — предпочесть цель T0 при выборе задач). Полётом (стабилизация, управление моторами) занимается PX4, а траекторию и обход препятствий считает `flight_ctrl.py`.
- Системного промпта у System 1 нет. Промпты есть только у компилятора приказов и у System 2.

Что показал прогон за 20 минут (все борта): команд System 1 — 8 SCAN_TARGET, 8 DECLARE_FAILOVER (6 про борт 2, 2 про борт 5, который жив), 1 HOLD_SECTOR, 1 EVADE_JAMMING (отклонена); команд System 2 — 0 (все вызовы по таймауту). Задержка System 1 — медиана 0,1–0,8 мс, p95 0,3–15 мс; но 99,7 % тактов результат «ничего не делать» (`idle`), а задержка эмбеддера p95 около 13,5 с — на практике этот путь не работает в реальном времени. Две команды «борт 5 отказал» при живом борте 5 — похоже на ложное срабатывание при глушении; не разбиралось.

Перемер эмбеддера 2026-11-02 (`logs/embed_bench_20261102_1620/`, один прогон). EmbeddingGemma-300m int8, 1 поток ORT. Отдельно при остановленном стенде: 226 мс медиана, p95 260 мс; пять процессов одновременно: около 510 мс, p95 около 600 мс. Живой стенд, сценарий 05 (приказ «Браво», РЭБ, потеря борта 2), 8 минут, load 5-18: эмбеддер вызывается только когда сработало правило, то есть 1-2 раза на борт за прогон; каждый раз промах кэша, кодирование 5,4-5,8 с, потому что первое срабатывание (R9 сразу после приказа) совпадает с разбором приказа llama-server на всех пяти бортах (10 с, load до 18, свободной памяти с 3,5 до 1 ГБ). Итог: все 7 команд System 1 за прогон приняты путём `rules+miss`, путь `hybrid` не встретился ни разу; эмбеддинг ни на одно решение не повлиял, задержку решения не увеличивает (команды за 2-46 мс). Текст состояния собран из дискретных значений (фаза, связь, GPS, sigma, молчание, потери, задача), поэтому близости можно посчитать заранее при сборке образа или выключить эмбеддер (`S1_MODE=rules`), это решение владельца.
Прогон с `S1_ENABLE=0` (2026-10-28, один прогон): миссия прошла так же — Браво выполнен, цель T0 с evidence-кадром, борт 2 потерян и задачи перераспределены. Флаг отключает только команды System 1; определение фазы продолжает работать. Вывод: в демо System 1 — защитный слой, а не источник видимых решений.
Как проверить самому: `S1_ENABLE=0 ./scripts/swarm_fresh.sh`, затем `DEMO_AUTOPILOT=1 ./scripts/run_demo.sh`, и сравнить журнал (`cmd S1:`) с обычным прогоном; юнит-тесты — `test_matcher`, `test_actions`, `test_features_phase`, `test_flow`, `test_injection` в контейнере агента.

## 7. Сценарий «Каскад» (System 1 + System 2)

Запуск (после `./scripts/swarm_fresh.sh`, сразу, пока рой ждёт приказа):

```bash
DEMO_AUTOPILOT=1 DEMO_SCENARIO=06_s1_s2_cascade DEMO_RF_AT_S=5 DEMO_KILL_AT_S=60 DEMO_KILL_DRONES="2 3 4" ./scripts/run_demo.sh
```

Что происходит: дрейф GPS на бортах 3 и 4, затем через 60 с от взлёта убираются борта 2, 3, 4. У двух выживших фаза SWARM_LOSS, подключается System 2 (LLM).

Результат прогона без mesh-помех (2026-10-28, один прогон): через 5 с после SWARM_LOSS System 2 на борту 1 выбрал SPLIT_SECTOR (сектор Браво S4 разделён на две части для двух выживших); на борту 5 такая же команда отклонена («уже разделён», сделал борт 1). Через ~20 с оба System 2 выбрали RETURN_HOME. System 1 при этом выдал только DECLARE_FAILOVER по убитым бортам; на дрейф GPS за 60 с реакции (HOLD_POSITION) не было.

Почему без mesh: при mesh L2 (50 % потерь) и L3 (80 %) живые борта через ~15 с считают всех соседей мёртвыми (фаза SWARM_LOSS), System 1 объявляет отказ живых, System 2 уводит рой домой ещё до убийства бортов; связь возвращается через 15-25 с после снятия помехи (прогоны с L3 и L2). Это отдельная проблема, она записана в `docs/HANDOFF_OPEN_PROBLEMS.md`.
