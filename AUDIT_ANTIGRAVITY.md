## A. Заявления в демо/HUD, которые код не подтверждает (самое важное для инвесторов)

**A1. «Обнаружение цели» не существует — цели известны заранее.** (В)
- `common.py:93-94`: задачи-цели строятся из `SCENE["targets"]` — координаты T0..T3 лежат в списке задач с самого старта.
- `evidence.py:54-60`, `:95`: `target_id` в BDA-карточке = `nearest_target(x, y)`, то есть ближайшая к *оценённой позиции борта* цель из `scene.json`. Картинка в расчёте не участвует.
- `CLAUDE_PROJECT_BRIEF.md:13` говорит «Зависание над обнаруженной целью, удержание визуального контакта».
- Итог: карточка «Цель T0, дистанция 1.2 м» = «борт прилетел в заранее известную точку». Это не детекция. Если борт ошибётся в позиции, карточка всё равно подпишет ближайшую цель.

**A2. Демо-нарратив подогнан руками.** (В)
- `tasking.py:21-26`: комментарий прямо говорит, что Bravo→S4 выбран так, чтобы «гарантировать срабатывание демо-нарратива».
- `common.py:39`: `TARGET_PARENT_SECTOR = {6: 4, 7: 2, 8: 3}` задан вручную, а не выводится из сцены.
- Для 4-й цели (`SCENE.targets[:4]`, id 9) зоны нет: `coordinator.py:159-164` вернёт `(9-10)//2 = -1`, и задача никогда не станет активной.
- Это допустимо, если инвестору так и сказано. Сейчас в HUD этого не видно.

**A3. «Манифест согласован (5/5 бортов)» — это просто 5 HTTP 200.** (В)
- `app.js:354-355`: считает `results.filter(r => r.ok)`. Совпадение манифестов между бортами не проверяется (каждый борт компилирует Qwen отдельно, `tasking.py:63-90`; `cache_prompt: True` может давать расхождения).

- Итог: второй приказ из HUD молча ничего не делает, а UI пишет «согласован».

**A4. Вердикт `ACCEPTED` в логе решений ставится до решения координатора.** (В)
- `system1_controller.py:91` и `planner_bridge.py:123`: `"verdict": "ACCEPTED"` выставляется при публикации команды.
- Координатор потом может отклонить: `coordinator.py:345-351` (stale / phase mismatch / not permitted). HUD через `telemetry.py:54,61` показывает «ACCEPTED» и для отклонённых команд. Реальный результат лежит только в `last_cmd.ok`.

**A5. «VIO» — это оптический поток, а «sigma» — выдуманная формула.** (В)
- `vio_node.py`: фазовая корреляция кадров, интегрирование смещения. Нет инерциальной части и нет карты, так что это не VIO. Дрейф не ограничен.
- `flight_ctrl.py:109,113`: `sigma += (0.02*|v| + 0.02)*dt` и `(0.05*|v| + 0.1)*dt`. Это константы, не ковариация фильтра. HUD и `phase.py` используют это как «ошибку позиции в метрах».
- `vio_node.py:43-45`: высота `self.h` никогда не протухает. Если нижний дальномер замолчит, масштаб потока останется по старому значению.

**A6. Бенчмарк «p95 ≤ 50 мс» может быть на синтетике.** (С)
- `bench_decision.sh` режим `micro` зовёт `tools/bench_s1.py`, который импортирует `swarm.synth.synth_state` (`bench_s1.py:15`). Файл целиком не читал. В режиме `live` меряется `dt_ms` S1-решений, S2 (секунды) туда не входят.

## C. Путь полёта и консенсуса

**C1. После взлёта нет контроля состояния борта.** (В; как причина D4 — С)
- `flight_ctrl.py:213-218`: после `TAKEOFF → FLY` ни `arming_state`, ни высота больше не проверяются. `ARMING` только из `WAIT`.
- Если PX4 разоружился (failsafe, land), `flight_ctrl` продолжает публиковать `NAV`/`HOLD`, а координатор считает задачи по оценённой позиции (`coordinator.py:523-525`). Это совпадает с наблюдением «D4 на земле, HUD говорит NAV».

**C2. Цепочка «GPS потерян → sigma растёт → CRITICAL → RETURN_HOME навсегда».** (В по коду; время — расчёт)
- `phase.py:14`: `sigma > 40` → `CRITICAL`; `matcher.py:26`: `RETURN_HOME` в CRITICAL = 0.95, S1 исполняет без LLM; `coordinator.py:419-425`: `withdrawn = True`, выхода нет (только рестарт).

**C3. Обмен между бортами: один общий ключ, нулевой ключ по умолчанию, нет защиты от повторов.** (В)
- `wire.py:7`: `os.environ.get("SWARM_KEY", "00" * 16)` — без переменной ключ нулевой молча.
- `wire.py:9`: тег HMAC 4 байта.

**C4. Тайм-аут манифеста запускает полный облёт.** (В)

**F1. Поля приказа `on_target`, `dwell_s`, `rtb_on_complete` ни на что не влияют.** (В)

**F2. «Свойственные» тесты G2 не могут упасть.** (В)

Это тавтология: «0 нарушений» не доказывает ничего, пока фильтр стоит в конце функции. **F3. `bench_decision.sh live` не работает.** (В)
- Скрипт вызывает `collect_topic.py --duration N --key swarm/local/s1_log`, а скрипт принимает позиционные `<topic> <seconds>` (`collect_topic.py:11-12`): топиком станет «--duration». Даже при исправлении вывод имеет вид `{"rx", "msg": {...}}`, а анализатор ищет `dt_ms`/`latency_ms` на верхнем уровне. Результат всегда «нет записей с латентностью».

**F4. «Нейросеть» System 1.** (В)
- `features.py` дискретизирует состояние в 7 полей с 3–6 значениями, `embedder.py` кодирует получившуюся строку, `prototypes.py` содержит 20 вручную написанных эталонных ситуаций. Матчер сравнивает эмбеддинг с эталонами и даёт не более 40 % веса; решение уже отфильтровано правилами (`rule_score` = 0 исключает действие). Это ближайший сосед над закрытым словарём, а не обучение или понимание ситуации.
- `bench_s1.py` меряет путь решения на синтетических состояниях (`synth.py`: независимые случайные поля, `total_tasks = 10` вместо 22, нет реальных корреляций) и без ожидания эмбеддинга: при промахе кэша `decide()` не ждёт. Холодный эмбеддинг считается отдельно, это честно, но цифру «p95 ≤ 50 мс» нужно подписывать «путь решения, без эмбеддинга, синтетические состояния».
